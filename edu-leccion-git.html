Control de versiones

Git y GitHub
desde cero

Controla versiones de tu código, colabora sin pisar el trabajo de otros y publica proyectos con seguridad. Aprende los conceptos y comandos fundamentales de Git y el flujo de trabajo en GitHub.

Qué es Git y qué es GitHub

Git es un sistema de control de versiones distribuido creado para rastrear cambios en archivos y coordinar trabajo entre desarrolladores. Cada copia del repositorio contiene el historial completo, lo que permite trabajar sin conexión y mantener integridad mediante hashes criptográficos. GitHub es una plataforma alojada que agrega colaboración sobre repositorios Git: pull requests, issues, revisiones, acciones de CI/CD y gestión de permisos.

El modelo mental clave: Git guarda snapshots del proyecto a lo largo del tiempo. Cada commit apunta a un árbol de archivos y a su(s) commit(s) padre, formando un historial navegable y auditable.

Conceptos base

Working directory (tus archivos), staging area/index (lo que prepararás para confirmar) y repository (historial confirmado). Mueves cambios entre estas áreas con git add y git commit.

Configuración inicial

Tras instalar Git (git-scm.com), configura tu identidad — quedará registrada en cada commit:

git --version
git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"
git config --global init.defaultBranch main
git config --list

Para autenticarte con GitHub se recomienda HTTPS con credenciales cacheadas o SSH con llaves. Genera una llave SSH y agrégala a tu cuenta de GitHub para operaciones seguras sin escribir contraseña en cada push.

ssh-keygen -t ed25519 -C "tu@correo.com"
# Copia la clave pública (~/.ssh/id_ed25519.pub) a GitHub > Settings > SSH keys
ssh -T git@github.com

Crear y clonar repositorios

# Iniciar un repo nuevo en la carpeta actual
git init

# Clonar un repo existente
git clone https://github.com/usuario/proyecto.git
git clone git@github.com:usuario/proyecto.git

Al clonar obtienes el historial completo y un remoto llamado origin que apunta a la URL de origen. Puedes inspeccionar remotos con git remote -v.

Flujo básico: status, add, commit

El ciclo diario consiste en modificar archivos, revisar cambios, preparar y confirmar:

git status                 # qué cambió y qué está staged
git diff                   # cambios no staged
git diff --staged          # cambios preparados
git add archivo.txt        # agrega archivo al staging
git add .                  # agrega todos los cambios del directorio
git commit -m "Describe el cambio en imperativo"

Escribe mensajes claros: “Agrega validación de correo” en lugar de “cambios”. Commits pequeños y atómicos facilitan revisión, bisect y revert. Para ver el historial usa git log --oneline --graph --decorate.

Ignorar archivos

Crea un .gitignore para excluir artefactos generados, dependencias y secretos (node_modules/, .env, dist/, __pycache__/). Nunca versiones credenciales.

Ramas, merge y resolución de conflictos

Las ramas permiten desarrollar características aisladas sin afectar main. Una rama es un puntero móvil a un commit.

git branch                  # lista ramas locales
git branch feature/login    # crea rama
git switch feature/login    # cambia a la rama (o: git checkout feature/login)
git switch -c fix/bug-123   # crea y cambia en un paso

# Integrar cambios a main
git switch main
git merge feature/login

Si dos ramas modifican las mismas líneas, Git detiene el merge y marca conflictos. Debes editar los archivos, elegir el contenido correcto, quitar los marcadores <<<<<<</=======/>>>>>>>, y luego git add + git commit. Para historiales lineales algunos equipos prefieren git rebase, pero úsalo con cuidado en ramas compartidas.

Trabajo remoto y Pull Requests

Sincroniza tu repositorio local con GitHub:

git remote add origin git@github.com:usuario/proyecto.git
git push -u origin main        # publica main y establece upstream
git pull                       # trae y fusiona cambios remotos
git fetch                      # descarga sin fusionar

El flujo colaborativo típico en GitHub: crea una rama, sube commits, abre un Pull Request (PR) hacia main, solicita revisión, atiende comentarios, pasa checks automáticos y fusiona. El PR documenta la intención del cambio y permite discusión antes de integrarlo.

  • Mantén tu rama actualizada: git fetch origin y git merge origin/main o rebase según política del equipo.
  • Usa PRs pequeños y enfocados; enlaza issues cuando aplique.
  • Protege main con reglas de rama (revisión obligatoria, CI verde).

Deshacer y recuperar

Git ofrece herramientas seguras para corregir errores sin perder historial:

git restore archivo.txt            # descarta cambios no staged
git restore --staged archivo.txt   # saca del staging
git revert <commit>                # crea un commit que revierte otro (seguro en remoto)
git reset --soft HEAD~1            # deshace último commit manteniendo cambios staged
git stash                          # guarda trabajo en progreso temporalmente
git stash pop                      # recupera el stash

Evita reset --hard y push --force en ramas compartidas salvo que sepas exactamente las consecuencias. git reflog puede ayudarte a localizar commits perdidos localmente.

Checklist de colaboración

Haz pull antes de empezar, trabaja en ramas, commitea con mensajes claros, revisa git status antes de confirmar y abre PRs para todo cambio relevante. Así el historial cuenta una historia coherente del proyecto.
