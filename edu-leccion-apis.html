APIs REST:
consumir y crear

Las APIs conectan aplicaciones entre sí: tu app pide datos a un servicio y recibe respuestas estructuradas. Aquí aprenderás los fundamentos HTTP, cómo consumir APIs y cómo diseñar endpoints REST claros.

Qué es una API REST

Una API (Application Programming Interface) define cómo dos piezas de software se comunican. En la web, las APIs más comunes siguen el estilo REST (Representational State Transfer), que aprovecha HTTP: recursos identificados por URLs, operaciones expresadas con métodos HTTP y respuestas normalmente en JSON. REST no es un protocolo estricto sino un conjunto de restricciones arquitectónicas descritas por Roy Fielding: interfaz uniforme, stateless, cacheable y sistema en capas.

Piensa en un recurso como “usuarios” o “pedidos”. Un endpoint como /api/users/42 identifica un recurso concreto; el método HTTP indica la intención (leer, crear, actualizar, borrar). Esta uniformidad hace que las APIs sean predecibles y fáciles de integrar.

Cliente, servidor y contrato

El cliente (navegador, app móvil, script) envía una petición; el servidor procesa y devuelve una respuesta con código de estado, cabeceras y cuerpo. La documentación de la API es el contrato: URLs, parámetros, formatos y errores esperados.

Métodos HTTP y semántica

  • GET: lee un recurso. Debe ser seguro (no modifica estado) e idempotente. Ej.: GET /products?category=tools.
  • POST: crea un recurso o ejecuta una acción. No es idempotente por defecto. Ej.: POST /orders.
  • PUT: reemplaza un recurso completo en una URL conocida. Idempotente.
  • PATCH: actualiza parcialmente un recurso.
  • DELETE: elimina un recurso. Idempotente en intención.

Las cabeceras transportan metadatos: Content-Type: application/json indica el formato del cuerpo; Accept indica lo que el cliente espera; Authorization porta credenciales.

GET /api/v1/products/123 HTTP/1.1
Host: api.ejemplo.com
Accept: application/json
Authorization: Bearer <token>

Códigos de estado

El código HTTP comunica el resultado sin ambigüedad. Conocerlos acelera el diagnóstico:

  • 2xx Éxito: 200 OK (respuesta con datos), 201 Created (recurso creado), 204 No Content (éxito sin cuerpo, típico en DELETE).
  • 3xx Redirección: 301/308 movido permanente, 304 Not Modified (caché válida).
  • 4xx Error del cliente: 400 Bad Request (datos inválidos), 401 Unauthorized (no autenticado), 403 Forbidden (sin permiso), 404 Not Found, 429 Too Many Requests (rate limit).
  • 5xx Error del servidor: 500 Internal Server Error, 502/503 problemas de upstream o disponibilidad.

Errores útiles

Una buena API devuelve errores en JSON con un mensaje claro, un código interno y, cuando aplique, detalles de validación. Evita exponer trazas internas al cliente.

Consumir una API con fetch y curl

Desde JavaScript en el navegador o Node, la Fetch API (MDN) es el estándar moderno. Desde terminal, curl es imprescindible para pruebas rápidas.

# curl: GET con cabeceras
curl -s https://api.github.com/repos/nodejs/node | head
curl -X POST https://api.ejemplo.com/orders \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer TOKEN" \
  -d '{"productId":123,"qty":2}'
// fetch (JavaScript)
async function obtenerProductos() {
  const res = await fetch('https://api.ejemplo.com/products', {
    headers: { 'Accept': 'application/json' }
  });
  if (!res.ok) throw new Error('HTTP ' + res.status);
  const data = await res.json();
  return data;
}

En Python, la librería requests simplifica el consumo: requests.get(url, headers=..., params=..., timeout=10) y response.json(). Maneja siempre timeouts, errores de red y códigos no exitosos.

Autenticación y seguridad

  • API Keys: identifican al cliente; se envían en cabecera o query. Trátalas como secretos.
  • Bearer tokens / OAuth 2.0: tokens de acceso con scopes y expiración, estándar para delegar autorización.
  • HTTPS obligatorio: protege credenciales y datos en tránsito.
  • Rate limiting: respeta límites; implementa reintentos con backoff ante 429.
  • CORS: los navegadores restringen peticiones cross-origin; el servidor debe enviar cabeceras adecuadas.

Nunca incrustes secretos en el frontend público. Usa variables de entorno en el servidor y rota claves comprometidas.

Diseñar y crear una API REST simple

Un diseño REST claro nombra recursos con sustantivos en plural, usa jerarquías lógicas y mantiene consistencia. Ejemplo de endpoints para un catálogo:

GET    /api/v1/products        → lista productos
GET    /api/v1/products/123    → detalle
POST   /api/v1/products        → crea
PATCH  /api/v1/products/123    → actualiza parcial
DELETE /api/v1/products/123    → elimina

Ejemplo mínimo con Node.js y Express:

import express from 'express';
const app = express();
app.use(express.json());

let items = [{ id: 1, name: 'Laptop' }];

app.get('/api/v1/items', (req, res) => res.json(items));
app.post('/api/v1/items', (req, res) => {
  const item = { id: Date.now(), name: req.body.name };
  items.push(item);
  res.status(201).json(item);
});

app.listen(3000, () => console.log('API en :3000'));

Buenas prácticas de diseño

Versiona la API (/v1), valida entradas, pagina colecciones, documenta con OpenAPI/Swagger y devuelve formatos consistentes. Diseña para la idempotencia donde sea posible y registra solicitudes para observabilidad.
